The ownership rule in this lab is basically that once a token is successfully added to the list, the list is reposnisble for it. This also means the list is responsible for the lexeme insinde the token. As the code assumes that the list takes ownership on push. I followed this rule by putting the token inside the new tokenNodes when list_push_back or list_puush_front succeeds.
When a token is first created with token_make, its lexeme is copied onto the heap so that memory has to eventually be freed. Once the token is put into the list,the list owns it. when the list is destroyed, list_destroy goes through each nodes saves the next node, calls the token_free on the current token and then frees the node. This makes sure both the lexeme and the node are cleaned up.
The same idea happens when a token is removed from the list. My list_remove_first function unlinks the node first then calls token_free on its token before using free on the node. This is important because freeing the node without freeing its token's lexeme would leave memory behind.
If push_back failed to allocate a node and i didnt free the token, the lexeme would be left in memory with nothing owning it anymore. that would cause a memory leak. This is why my push_back calls token_free(&token) when malloc fails. That way, whether the token is successfully added or the insertion fails, the memory for its lexeme is eventually freed exactly once.
